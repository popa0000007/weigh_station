# Как устроен проект и почему

Документ для того, кто видит .NET-решение впервые. Читать сверху вниз.

## 1. Что такое «решение», проект и сборка

```
WeighStation.sln                  ← «папка с проектами»: список, что собирать вместе
├─ src/WeighStation.Core          ← проект = один .csproj = одна сборка (.dll)
├─ src/WeighStation.Infrastructure
├─ src/WeighStation.Presentation
├─ src/WeighStation.App           ← единственный, который превращается в .exe
└─ tests/WeighStation.Core.Tests
```

* **`.csproj`** — XML-описание проекта: целевая платформа (`net8.0`), пакеты (`PackageReference`), ссылки на соседние проекты (`ProjectReference`).
* **`Directory.Build.props`** лежит в корне и автоматически подмешивается во все `.csproj`: общие настройки (`Nullable`, `TreatWarningsAsErrors`) задаются один раз.
* **Сборка** (`dotnet build`): 1) *restore* скачивает NuGet-пакеты; 2) MSBuild собирает проекты в порядке зависимостей; 3) компилятор C# (Roslyn) превращает `.cs` в `.dll`; 4) в WPF-проекте перед этим ещё компилятор разметки превращает `.xaml` в бинарный BAML + сгенерированный `.g.cs`.
* `net8.0-windows` у `WeighStation.App` означает «только Windows»: WPF — это обёртка над Windows-графикой. Остальные проекты — обычный `net8.0`, поэтому их можно собирать и тестировать на любой ОС.

## 2. Слои и правило зависимостей

```
          ┌────────────────────┐
          │  WeighStation.App  │  окна, стили, диалоги, печать, точка входа (только Windows)
          └─────────┬──────────┘
                    │ знает про всех
   ┌────────────────┼──────────────────┐
   ▼                ▼                  ▼
Presentation   Infrastructure         Core
(ViewModel-и)  (SQLite, JSON,         (правила: цикл взвешивания,
   │            симулятор)             отчёты, интерфейсы устройств)
   └──────────────────────┴────────────▶ Core
```

Стрелки — «использует». **Core не знает ни про что**: ни про базу, ни про окна, ни про ПЛК. Он описывает *что нужно* интерфейсами (`IScale`, `IPlatformIo`, `IWeighingRepository` …), а *как* — решают другие проекты. Отсюда три выгоды:

1. **Тестируемость.** Логику цикла (светофор, шлагбаум, стабильность веса) проверяют обычные тесты с подставными устройствами — без весов и без окон.
2. **Замена частей.** Симулятор → настоящий драйвер ПЛК: меняется одна строка в `App.xaml.cs`, остальное не трогается.
3. **Безопасность изменений.** Нельзя случайно вызвать окно из логики шлагбаума — проект просто не видит WPF.

Место, где всё связывается, называется **composition root** (`App.xaml.cs`, метод `OnStartup`): единственное место с `new SqliteWeighingRepository(...)`. Остальной код получает зависимости через конструктор.

## 3. MVVM: как экран связан с логикой

* **View** (`Views/*.xaml`) — только разметка. Кода в `*.xaml.cs` почти нет.
* **ViewModel** (`WeighStation.Presentation`) — состояние экрана и команды: `WeightText`, `CanCapture`, `CaptureCommand`. Не знает, что такое окно.
* **Связь** — *привязки*: `Text="{Binding WeightText}"`. WPF подписывается на `PropertyChanged` и сам обновляет элемент.
* Какой View рисует какую ViewModel, записано в `App.xaml` (`DataTemplate DataType=…`).
* Генераторы `CommunityToolkit.Mvvm`: поле `[ObservableProperty] _weightText` превращается в свойство `WeightText` с уведомлением; метод `[RelayCommand] Capture()` — в `CaptureCommand`.

ViewModel-и вынесены в отдельный проект **потому что они не используют WPF-типы**. Благодаря этому они тестируются на Linux так же, как на Windows (см. `tests/.../Presentation`). Всё, что требует Windows (диалог сохранения, печать, `Dispatcher`), спрятано за интерфейсами `IDialogService`, `ITicketPrinter`, `IUiContext`.

## 4. Потоки

Весы и камеры присылают данные из фоновых потоков, а изменять привязанные объекты WPF разрешает только UI-потоку. Поэтому:

* `WeighingSession` потокобезопасна (`lock`), события поднимает **вне** блокировки;
* ViewModel подписывается и перебрасывает обработку через `IUiContext.Post` (в WPF это `Dispatcher.BeginInvoke`);
* `BeginInvoke`, а не `Invoke`: поток весов не должен ждать интерфейс.

## 5. Цикл взвешивания

```
Idle ──въезд/платформа──▶ Entering ──ТС целиком──▶ Weighing ──вес стабилен + номер──▶ ReadyToCapture
 ▲   (светофор зелёный)    (зелёный)               (красный)                              │ Capture
 └────── ТС уехало ◀── Exiting (шлагбаум открыт, светофор красный) ◀── вес записан в БД ──┘
```

Ключевые решения (все закреплены тестами):

* **Шлагбаум открывается только после успешной записи** в БД. Не записалось → остаётся закрытым, можно повторить.
* **Стабильность** — два независимых признака: собственное окно (`StabilityTracker`) и флаг терминала.
* **Сторожевой таймер весов**: тишина дольше `ScaleTimeout` блокирует запись. Без него «последний стабильный» вес висел бы вечно. Для этого `Tick()` вызывается раз в секунду.
* После паузы в данных окно стабильности начинается заново.
* Очередь на въезде не держит шлагбаум открытым.
* Номера хранятся в одном виде (`PlateNumber.Normalize`): камеры возвращают латиницу вместо кириллицы, операторы вводят с пробелами.

## 6. Данные

SQLite-файл `%LOCALAPPDATA%\WeighStation\weighings.db`. Схему создаёт `SqliteDatabase` (одно место). Таблицы: `weighings`, `weighing_history` (кто и что менял), справочники `vehicles`, `companies`, `cargos`, `drivers`.

* Запись взвешивания и её истории — в одной транзакции.
* Резервная копия — через API онлайн-копирования SQLite (`BackupDatabase`), а не `File.Copy`: файл может быть в момент записи.
* Отмена записи не удаляет её; отменённые не попадают в отчёты и в поиск тары.

## 7. Как это проверено

| Уровень | Что проверяет | Где |
|---|---|---|
| Юнит-тесты | цикл, стабильность, номера, отчёты, CSV | `tests/.../*.cs` |
| Интеграционные | SQLite, справочники, настройки, резервная копия | `InfrastructureTests` |
| ViewModel-тесты | каждый экран: команды, валидация, ошибки | `tests/.../Presentation` |
| Сквозные | всё приложение на симуляторе, с потоками | `EndToEndTests` |
| Статика XAML | опечатки в привязках, ресурсах, значениях, свойствах | `tests/.../Xaml` |

Статическая проверка XAML нужна потому, что WPF молчит об опечатке в `{Binding}`, а неверный ключ ресурса падает только при открытии экрана. Проверка читает настоящие определения WPF-контролов из reference-сборок (NuGet `Microsoft.WindowsDesktop.App.Ref`) — Windows для этого не нужен. Тесты проверяют и сам проверяющий: в реальные экраны подставляются опечатки, и они должны находиться.

**Что тестами не покрыто:** внешний вид, реальные диалоги/печать Windows, настоящее оборудование. Это проверяется запуском на Windows.
